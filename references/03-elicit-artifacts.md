# 03 – Elicit Artifacts: 스킬/에이전트/DMN 후보 제시 + 선택 (HITL)

**목적**: 1단계에서 만든 프로세스 정의 JSON 을 분석해 **재사용 스킬 · 에이전트 · DMN 의사결정 후보**를 뽑고, 사용자에게 *무엇을 만들지* 한 번에 묻는다. 사용자가 고른 것만 실제로 만든다. 이것이 이 skill 의 핵심 **HITL(Human-In-The-Loop)** 단계다.

> pdf2bpmn 의 "통합 elicit" 흐름을 옮긴 것입니다. 스킬/에이전트/DMN 후보를 **한 번**에 함께 묻되, **반드시 `request_human_input`** 으로 묻습니다(아래 "사용자에게 묻기").

산출물: 선택 결과를 받아 선택분만 스킬(skill-creator 로 생성, workspace 산출물 파일)/에이전트/DMN 으로 만들고 `/workspace/.bpmn/process-definition.json` 에 반영한다.

---

## 핵심 원칙

0. **🔴 반드시 "구체 후보를 나열한 선택 질문"이어야 한다 (빈 질문/빈 후보 금지).**
   - 질문 **전에** 먼저 프로세스 elements 에서 종류별(스킬/에이전트/DMN) **구체 후보 3개 내외를 도출**한다(아래 "후보 도출 규칙"). 이 도출을 건너뛰고 질문부터 내보내면 안 된다.
   - **반드시 `request_human_input` 도구(interrupt)로** 묻는다(프로즈로 끝내지 말 것 — 09 "단일 세션 실행"). request_human_input 엔 `suggestions`/`items` 인자가 없으므로, **후보를 `question` 텍스트에 아래 형식으로 나열**한다(프론트가 이 형식을 파싱해 선택 패널을 렌더한다). **후보 없는 빈 질문은 명백한 위반**(화면에 고를 게 없어 멈춘다).
     ```
     이 프로세스에 추가할 스킬·에이전트·DMN 을 골라주세요 (안 고르면 건너뜁니다):

     [스킬]
     • 휴가 잔여일수 검증: 신청 전 잔여 연차 확인
     • 결재 검토 처리: 신청서 기준 검토·승인
     • 결과 통보 발송: 승인/반려 결과 통보
     [에이전트]
     • 팀장 — 휴가 검토: 검토·승인 담당
     • 인사팀 — 휴가 등록: 승인 휴가 반영
     [DMN]
     • 승인 여부 판단: 승인→등록 / 반려→통보
     ```
   - 금지 예: "어떤 스킬/에이전트/DMN 을 추가할까요?"(후보 없음)·"…만들까요?"(생성여부) — 절대 금지. 모호어 '자동화 요소' 같은 표현도 쓰지 않고 **스킬·에이전트·DMN** 을 그대로 쓴다.
   - 정말 도출되는 후보가 0개인 극히 예외적 경우에만, 질문 대신 "추가할 스킬·에이전트·DMN 이 없어 보입니다. 바로 폼·참조정보로 진행할게요" 라고 안내하고 다음 단계로 넘어간다(빈 질문 금지).
1. **묻지 않고 다 만들지 않는다.** 후보를 보여주고 선택을 받는다. 아무것도 안 고르면 그 종류는 건너뛴다. 강요 금지.
2. **한 번에 묻는다.** 스킬·에이전트·DMN 을 따로 여러 번 묻지 말고, 한 번의 `request_human_input` 에 세 섹션을 함께 넣는다. 후보가 없는 종류는 뺀다.
3. **후보는 JSON 에서 도출한다.** 지어내지 말 것. 아래 도출 규칙대로 실제 elements 를 근거로 후보를 만든다.
4. **선택 후 즉시 반영.** 사용자가 고르면 스킬/에이전트/DMN 을 선택된 것만 생성하고 `process-definition.json` 을 업데이트한다.

## 후보 도출 규칙

> **추천 개수 목표**: 각 종류(스킬/에이전트/DMN)마다 **3개 내외의 후보를 적극적으로 추천**하는 것을 목표로 한다(가능하면 3개). 작은 선형 프로세스라도 재사용·자동화·판단 자동화 관점에서 의미 있는 후보를 발굴해 채운다. 후보가 정말 1~2개뿐이면 그대로 두고, 전혀 없으면 그 종류의 질문 자체를 만들지 않는다. 후보는 반드시 실제 elements 에 근거해야 하며, 지어내거나 프로세스와 무관한 것을 넣지 않는다.

### 스킬 후보 (→ [04-skills.md](04-skills.md))
재사용 가능한 "공통 작업"을 찾는다. 근거:
- 여러 Activity 의 `instruction`/`description` 이 **유사한 의도**로 반복되면(예: "기준 대조 검토", "서류 확인") 그 묶음을 스킬 후보 1개로.
- 단일 Activity 라도 그 자체로 **독립적·재사용성 높은 절차**(예: "정책 기준 일치성 검증")면 후보가 될 수 있다.
- 후보 1개 = `{ id(safe_name kebab-case), label(한글 스킬명), description(1줄), source_activity_ids(근거 액티비티) }`.
- 후보가 없으면(작은 선형 프로세스) 스킬 질문 자체를 만들지 않는다.

### 에이전트 후보 (→ [05-agents.md](05-agents.md))
"역할 + 그 역할이 반복 수행하는 스킬" 조합을 에이전트 후보로.
- 근거: `roles` 와, 각 역할이 담당하는 Activity 묶음. 스킬 후보가 있으면 (역할 × 스킬) 로 매칭.
- 후보 1개 = `{ candidate_id("agent_<역할>_<스킬>"), label("역할명 — 스킬명"), description("담당 활동 N개 · 역할/목표 요약"), role_name, activity_ids }`.
- 조직도 등 기존 에이전트 정보가 있으면 "기존 재사용" 으로 표시(신규 생성 안 함). 이 skill 의 일반적 상황(조직도 없음)에서는 전부 신규 후보.

### DMN 후보 (→ [06-dmn.md](06-dmn.md))
분기 판단을 의사결정 테이블로 만들 가치가 있는 게이트웨이를 찾는다. 자격:
- `type` 이 **ExclusiveGateway** 이고 (Parallel/Inclusive 는 제외 — 조건 평가 의미가 다름),
- outgoing Sequence 가 **2개 이상**.
- 같은 이름의 게이트웨이가 여러 개면 **하나의 후보로 병합**.
- 후보 1개 = `{ candidate_id("dmn::<gateway_id>"), label("[프로세스명] 게이트웨이명"), description("분기 N개: 조건1 → 대상1 / 조건2 → 대상2"), gateway_ids }`.

## 사용자에게 묻기 — `request_human_input` (필수)

**반드시 `request_human_input` 도구**로 묻는다(프로즈로 끝내거나 done 으로 턴을 종료하지 말 것 — interrupt 로 멈춰야 같은 세션이 유지된다). `request_human_input` 에는 `options`/`items`/`suggestions` 인자가 **없으므로**, 후보를 아래 형식 그대로 **`question` 텍스트에 나열**한다. 프론트가 이 `[종류]` 섹션 + `• 라벨: 설명` 형식을 파싱해 **선택 패널**을 렌더한다.

**중요(형식)**: 후보 목록은 `request_human_input` 의 **`question` 인자**에 넣는다(`context` 아님 — 프론트는 question 을 파싱한다). 섹션 헤더는 **대괄호만**(`[스킬]`), 콜론(`[스킬]:`) 없이 쓴다. 문구에 모호한 표현을 쓰지 말고 **스킬·에이전트·DMN** 을 그대로 쓴다.

```
request_human_input(question="""
이 프로세스에 추가할 스킬·에이전트·DMN 을 골라주세요 (안 고르면 건너뜁니다):

[스킬]
• 휴가 잔여일수 검증: 신청 전 잔여 연차를 확인하는 공통 절차 (활동 2개)
• 결재 검토 처리: 신청서를 기준에 따라 검토·승인하는 절차 (활동 1개)
• 결과 통보 발송: 승인/반려 결과를 신청자에게 통보하는 공통 절차 (활동 2개)
[에이전트]
• 인사팀 — 휴가 검토: 검토·승인 활동 1개를 담당하는 신규 에이전트
• 인사팀 — 휴가 등록: 승인된 휴가를 근태/연차에 반영하는 에이전트
[DMN]
• 승인 여부 판단: 분기 2개 — 승인 → 휴가 등록 / 반려 → 신청자 통보
""")
```

- **반드시 구체 후보를 나열**한다. "어떤 스킬/에이전트/DMN 을 추가할까요?"(후보 없음)·"스킬/에이전트/DMN 을 만들까요?"(생성 여부) 같은 **빈 질문은 절대 금지** — 화면에 고를 게 없어 멈춘다.
- 후보가 없는 종류는 섹션 자체를 빼고, 모든 종류가 0개인 극히 예외적 경우에만 질문 대신 "추가할 스킬·에이전트·DMN 이 없어 보입니다. 바로 폼·참조정보로 진행할게요" 라고 안내하고 다음 단계로 넘어간다.
- 사용자가 추천 후보 외의 커스텀 요청(이름 변경, 새 스킬/규칙 추가 등)을 자유 입력으로 적으면 그 입력을 반영한다.
- 각 종류 후보는 **3개 내외**가 이상적이다. DMN 처럼 게이트웨이 수만큼만 나오면 1~2개여도 억지로 늘리지 않는다.
- 사용자에게 설명할 땐 용어를 풀어서: "스킬=반복 작업을 한 번 정의해 재사용", "에이전트=특정 역할을 자동으로 처리하는 담당", "DMN=갈림길 판단 규칙을 표로 정리".

## 선택 결과 처리

사용자 응답을 받은 뒤:

1. **스킬을 골랐으면** → [04-skills.md](04-skills.md) 로드 → 선택된 스킬만 **skill-creator 로 정식 스킬 생성**(workspace 산출물 파일) + JSON 반영.
2. **에이전트를 골랐으면** → [05-agents.md](05-agents.md) 로드 → 선택된 역할·스킬에 에이전트 연결 + JSON 반영.
3. **DMN 을 골랐으면** → [06-dmn.md](06-dmn.md) 로드 → 선택된 게이트웨이를 DMN 의사결정/규칙으로 생성 + JSON 반영.
4. 아무것도 안 골랐으면 → 바로 다음 단계(폼)로 진행한다.

> 의존성: 에이전트 후보는 스킬과 엮일 수 있으므로, 스킬 → 에이전트 → DMN 순으로 처리하는 것이 자연스럽다. 단 세 가지는 독립이므로 사용자가 고른 것만 해당 단계로 가면 된다.

## 멀티 프로세스일 때 — 프로세스마다 별도 패널로 묻는다

여러 프로세스를 만드는 중([11-multi-process.md](11-multi-process.md))이면, 멀티 프로세스는 **항상 일괄 고정 절차**(11단계 §4)로 진행하며 이 선택 단계는 그 **아티팩트 일괄 질문**에 해당한다. JSON 일괄 생성이 끝난 뒤, **각 프로세스마다 그 프로세스의 후보로 별도 패널을 띄워** 연달아 묻는다. 후보는 그 프로세스의 elements 에서 도출되므로 프로세스마다 다르며, **앞 프로세스의 선택을 자동 적용하거나 묻지 않고 자동 수락하지 않는다**(HITL 유지).

- 패널 헤더/질문에 **"[k/N: <프로세스명>]"** 라벨을 붙여 어느 프로세스 질문인지 분명히 한다.
- 한 프로세스당 이 패널은 1회뿐. **모든 프로세스의 패널을 다 받은 뒤** 후속 단계를 일괄 실행한다.
- **프로세스 간 재사용**: 사용자가 고른 결과가 앞 프로세스에서 이미 만든 것과 동일 의도면 중복 생성하지 말고 기존 id 를 연결한다(11단계 §5). 이는 자동 적용이 아니라 중복 제거다.

## 다음 단계 연결 (중요: 폼·참조정보는 자동 진행)

이 선택 단계는 **이 skill 에서 사용자에게 묻는 마지막 단계다.** 폼과 참조정보는 어떤 프로세스든 **항상 생성·연결해야 하는 필수 산출물**이므로, 여기서 *"폼을 만들까요?"* 같은 추가 질문을 **하지 않는다.**

사용자의 스킬/에이전트/DMN 선택을 반영한 뒤에는, **추가 확인 없이 곧바로** 아래를 **연속 자동 실행**한다:

1. 선택된 스킬/에이전트/DMN 생성 + JSON 반영 (위 "선택 결과 처리").
2. [07-forms.md](07-forms.md) 로드 → **모든 UserActivity 폼 자동 생성** + JSON 반영. (스킬/에이전트/DMN 을 하나도 안 골랐어도 진행한다.)
3. [08-reference-info.md](08-reference-info.md) 로드 → **inputData/conditionData 자동 연결** + JSON 최종 업데이트.

그런 다음 검증·완료 단계로 이어진다([09-service-execution.md](09-service-execution.md)). 단계 사이에 "다음으로 넘어갈까요?" 를 묻지 않는다.
