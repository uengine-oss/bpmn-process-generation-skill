# 03 – Elicit Artifacts: 스킬/에이전트/DMN 후보 제시 + 선택 (HITL)

**목적**: 2단계에서 만든 프로세스 정의 JSON 을 분석해 **자동화 요소 후보**(재사용 스킬 · 에이전트 · DMN 의사결정)를 뽑고, 사용자에게 *무엇을 만들지* 한 번에 묻는다. 사용자가 고른 것만 4·5·6단계에서 실제로 만든다. 이것이 이 skill 의 핵심 **HITL(Human-In-The-Loop)** 단계다.

> 이 단계는 pdf2bpmn 의 "통합 elicit" 흐름을 옮긴 것입니다. pdf2bpmn 은 스킬/에이전트/DMN 후보를 **한 패널에 묶어 사용자 개입 1회**로 받습니다. 우리도 동일하게 `AskUserQuestion` **한 번**으로 세 종류를 함께 묻습니다.

산출물: 별도 파일 없음. 사용자의 선택 결과를 4·5·6단계 입력으로 넘긴다. (선택 내역은 `.bpmn/01-consulting.md` 하단 "메모" 또는 대화로 유지)

---

## 핵심 원칙

1. **묻지 않고 다 만들지 않는다.** 후보를 보여주고 선택을 받는다. 아무것도 안 고르면 그 종류는 건너뛴다(`min_select=0` 와 동일). 강요 금지.
2. **한 번에 묻는다.** 스킬·에이전트·DMN 을 각각 따로 여러 번 묻지 말고, `AskUserQuestion` 한 호출에 여러 질문(question)으로 묶는다. 후보가 없는 종류는 질문에서 뺀다.
3. **후보는 JSON 에서 도출한다.** 지어내지 말 것. 아래 도출 규칙대로 실제 elements 를 근거로 후보를 만든다.
4. **선택 후 즉시 반영.** 사용자가 고르면 4(스킬)/5(에이전트)/6(DMN)단계 reference 를 로드해 선택된 것만 생성하고 `process-definition.json` 을 업데이트한다.

---

## 후보 도출 규칙

> **추천 개수 목표**: 각 종류(스킬/에이전트/DMN)마다 **3개 내외의 후보를 적극적으로 추천**하는 것을 목표로 한다(가능하면 3개). 작은 선형 프로세스라도 재사용·자동화·판단 자동화 관점에서 의미 있는 후보를 발굴해 채운다. 후보가 정말 1~2개뿐이면 그대로 두고, 전혀 없으면 그 종류의 질문 자체를 만들지 않는다. 후보는 반드시 실제 elements 에 근거해야 하며, 지어내거나 프로세스와 무관한 것을 넣지 않는다.

### 스킬 후보 (→ [04-skills.md](04-skills.md))
재사용 가능한 "공통 작업"을 찾는다. 근거:
- 여러 Activity 의 `instruction`/`description` 이 **유사한 의도**로 반복되면(예: "기준 대조 검토", "서류 확인") 그 묶음을 스킬 후보 1개로.
- 단일 Activity 라도 그 자체로 **독립적·재사용성 높은 절차**(예: "정책 기준 일치성 검증")면 후보가 될 수 있다.
- 후보 1개 = `{ id(safe_name kebab-case), label(한글 스킬명), description(1줄), source_activity_ids(근거 액티비티) }`.
- 후보가 없으면(작은 선형 프로세스) 스킬 질문 자체를 만들지 않는다.

### 에이전트 후보 (→ [05-agents.md](05-agents.md))
"역할 + 그 역할이 반복 수행하는 스킬" 조합을 에이전트 후보로.
- 근거: `roles` 와, 각 역할이 담당하는 Activity 묶음. 스킬 후보가 있으면 (역할 × 스킬) 로 매칭.
- 후보 1개 = `{ candidate_id("agent_<역할>_<스킬>"), label("역할명 — 스킬명"), description("담당 활동 N개 · 역할/목표 요약"), role_name, activity_ids }`.
- 조직도 등 기존 에이전트 정보가 있으면 "기존 재사용" 으로 표시(신규 생성 안 함). 이 skill 의 일반적 상황(조직도 없음)에서는 전부 신규 후보.

### DMN 후보 (→ [06-dmn.md](06-dmn.md))
분기 판단을 의사결정 테이블로 만들 가치가 있는 게이트웨이를 찾는다. 자격:
- `type` 이 **ExclusiveGateway** 이고 (Parallel/Inclusive 는 제외 — 조건 평가 의미가 다름),
- outgoing Sequence 가 **2개 이상**.
- 같은 이름의 게이트웨이가 여러 개면 **하나의 후보로 병합**.
- 후보 1개 = `{ candidate_id("dmn::<gateway_id>"), label("[프로세스명] 게이트웨이명"), description("분기 N개: 조건1 → 대상1 / 조건2 → 대상2"), gateway_ids }`.

## 사용자에게 묻기 (AskUserQuestion 1회)

후보가 있는 종류만 question 으로 만들어 **한 번에** 묻는다. 각 question 은 `multiSelect: true` (여러 개 고르거나 하나도 안 고를 수 있음). **종류마다 추천 후보를 3개 내외로 채워** 사용자가 클릭만으로 고를 수 있게 한다.

> **자동 "기타" 입력**: `AskUserQuestion` 은 모든 question 에 "기타(Other)" 자유 입력 옵션을 **자동으로 붙여준다.** 따라서 옵션 목록에 "기타"를 직접 만들지 말 것 — 사용자가 추천 후보 외의 커스텀 요청(이름 변경, 새 스킬/규칙 추가 등)을 적으면 그 입력을 반영하면 된다.

예시 (스킬·에이전트·DMN 후보가 모두 있는 경우 — 각 종류 3개 내외 추천):

```
AskUserQuestion(questions=[
  {
    header: "스킬",
    question: "[휴가 신청] 어떤 작업을 재사용 스킬로 만들까요? (안 고르면 건너뜁니다)",
    multiSelect: true,
    options: [
      { label: "휴가 잔여일수 검증", description: "신청 전 잔여 연차를 확인하는 공통 절차 (활동 2개)" },
      { label: "결재 검토 처리", description: "신청서를 기준에 따라 검토·승인하는 절차 (활동 1개)" },
      { label: "결과 통보 발송", description: "승인/반려 결과를 신청자에게 통보하는 공통 절차 (활동 2개)" }
    ]
  },
  {
    header: "에이전트",
    question: "[휴가 신청] 어떤 담당을 에이전트로 만들까요?",
    multiSelect: true,
    options: [
      { label: "인사팀 — 휴가 검토", description: "검토·승인 활동 1개를 담당하는 신규 에이전트" },
      { label: "인사팀 — 휴가 등록", description: "승인된 휴가를 근태/연차에 반영하는 에이전트" },
      { label: "인사팀 — 결과 통보", description: "처리 결과 통보를 담당하는 에이전트" }
    ]
  },
  {
    header: "DMN 규칙",
    question: "어떤 갈림길을 의사결정 표(DMN)로 만들까요?",
    multiSelect: true,
    options: [
      { label: "승인 여부 판단", description: "분기 2개: 승인인 경우 → 휴가 등록 / 반려인 경우 → 신청자 통보" }
    ]
  }
])
```

- 초심자에게는 용어를 풀어서: "스킬=반복 작업을 한 번 정의해 재사용", "에이전트=특정 역할을 자동으로 처리하는 담당", "DMN=갈림길 판단 규칙을 표로 정리".
- 질문은 최대 4개까지. 후보 종류가 3개(스킬/에이전트/DMN)이므로 보통 1~3개 question.
- 각 종류 옵션은 **3개 내외**가 이상적이다. DMN 처럼 후보가 게이트웨이 수만큼만 나오는 경우는 자연히 1~2개일 수 있다 — 억지로 늘리지 않는다.

## 선택 결과 처리

사용자 응답을 받은 뒤:

1. **스킬을 골랐으면** → [04-skills.md](04-skills.md) 로드 → 선택된 스킬만 카드 생성 + JSON 반영.
2. **에이전트를 골랐으면** → [05-agents.md](05-agents.md) 로드 → 선택된 역할·스킬에 에이전트 연결 + JSON 반영.
3. **DMN 을 골랐으면** → [06-dmn.md](06-dmn.md) 로드 → 선택된 게이트웨이를 DMN 의사결정/규칙으로 생성 + JSON 반영.
4. 아무것도 안 골랐으면 → "자동화 요소 없이 진행할게요" 하고 바로 5단계(폼)로.

> 의존성: 에이전트 후보는 스킬과 엮일 수 있으므로, 스킬 → 에이전트 → DMN 순으로 처리하는 것이 자연스럽다. 단 세 가지는 독립이므로 사용자가 고른 것만 해당 단계로 가면 된다.

---

## 다음 단계 연결 (중요: 폼·참조정보는 자동 진행)

3단계는 **이 skill에서 사용자에게 묻는 마지막 단계다.** 폼(5)과 참조정보(6)는 어떤 프로세스든 **항상 생성·연결해야 하는 필수 산출물**이므로, 여기서 *"폼을 만들까요?"* 같은 추가 질문을 **하지 않는다.**

사용자의 스킬/에이전트/DMN 선택을 받아 4단계(선택 아티팩트 생성)를 반영한 뒤에는, **추가 확인 없이 곧바로** 아래를 **연속 자동 실행**한다:

1. 4단계: 선택된 스킬/에이전트/DMN 생성 + JSON 반영 (위 "선택 결과 처리").
2. [07-forms.md](07-forms.md) 로드 → **모든 UserActivity 폼 자동 생성** + JSON 반영. (스킬/에이전트/DMN 을 하나도 안 골랐어도 진행한다.)
3. [08-reference-info.md](08-reference-info.md) 로드 → **inputData/conditionData 자동 연결** + JSON 최종 업데이트.

그런 다음 **마지막에 한 번** 무엇이 생성되었는지(흐름·역할/에이전트·스킬·DMN·폼·참조정보) 자연어로 요약하고, **"수정하고 싶은 부분이 있으면 말씀해 주세요"** 라고 안내한다. (완료 멘트 형식은 [08-reference-info.md](08-reference-info.md) 의 "완료 안내" 참조.)

> 즉, 사용자 개입은 3단계 선택 **한 번**으로 끝나고, 4·5·6단계는 그 답변 직후 자동으로 이어 붙은 뒤 한 번에 결과를 보고한다. 단계 사이에 "다음으로 넘어갈까요?" 를 묻지 않는다.
